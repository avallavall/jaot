# Backend audit — 2026-07-26

> Full read of `app/` (299 Python files, 61,149 lines) against ADR-001 (modular monolith,
> feature-led extraction), the project's own rules (`CLAUDE.md`, `app/CLAUDE.md`) and the
> bounded-context map (`docs/BOUNDED_CONTEXTS.md`).
>
> **Scope decision by the owner:** report only — no refactor commits. Every finding below
> was verified against the running system before being written down; the ones that turned
> out to be false are listed too, because "we checked and it is fine" is part of the answer.
>
> Companion documents: **ADR-009** (the concurrency rule this audit proposes) and the
> `D-10 … D-19` entries added to `TECH_DEBT.md` (the prioritised backlog).

## Verdict

The backend is in **good shape for its size**. There is no crisis: no cross-tenant leak, no
N+1 plague, no duplicated-logic sprawl, no wrong datetime handling, and the hardest path in
the product (solve) is already written with the right concurrency discipline *on purpose*.

What the audit found is **inconsistency, not ignorance**: the correct patterns exist and are
applied where somebody thought about them, and are absent everywhere nobody did. That is a
much cheaper problem to fix than a wrong design — but it is also the kind that quietly grows,
because each new endpoint is copied from whichever neighbour it sits next to.

The single systemic issue worth acting on before v4.0 is **concurrency** (F-01/F-02): 109 of
the API's endpoints block the event loop while they talk to the database.

## Method

Measurements were taken by scanning the tree and, where a claim depended on runtime
behaviour, by asking the running system (`docker exec jaot_api`, the local Postgres, and the
app's own router table) rather than by reading code alone.

## What is healthy (verified, not assumed)

| Area | Evidence |
|---|---|
| **Multi-tenancy** | 25 org-scoped ORM models; **0** `select()` on one of them without an `organization_id` filter in the statement. |
| **N+1 queries** | Only 2 loops in the whole tree issue a query inside the body, both at startup/seed (`main.py`, `seed_models.py`) — none on a request path. |
| **Datetime discipline** | All 10 `datetime.now(` call sites pass an explicit timezone (`timezone.utc` in JWT, user `tz` in scheduling). No naive `datetime.now()`. |
| **LLM client** | `AsyncAnthropic` with `await` / `async with` throughout — the long call is genuinely non-blocking. |
| **Solve path concurrency** | No solve runs inside the API process at all (ADR-007: one async pipeline, everything enqueued to Celery). The 6 endpoints that *wait* for a queued result are declared `def` **deliberately** (`# sync ON PURPOSE -> threadpool`, `# def: blocks on the queued result`) so the wait happens on a thread, not on the loop — exactly right. *(The 2 remaining `async def` endpoints in `solve.py` are status/cancel, not solving — see F-01.)* |
| **Code duplication** | Only 2 groups of byte-identical function bodies ≥8 lines (`_get_trigger_or_404`, `_listing_or_404`). |
| **Public surface** | All **37** publicly reachable routes enumerated from the live router and read one by one; every one is intentional. `POST /triggers/{id}/fire` is public *by design* and authenticates with a per-trigger secret, rate-limited (10/min, 500/day) **before** the DB lookup. |
| **Middleware** | Pure ASGI, no `BaseHTTPMiddleware`, per the project rule. |
| **Boundaries that are enforced** | 6 `import-linter` contracts: domains independent of each other, `shared` never imports domains, solver services never import `pyscipopt`, DSL compiler is a pure library. |
| **Test gate** | 203 test files, and CI does enforce coverage (`--cov-fail-under=78`) plus a Tier-1 test-quality checker and the E2E no-mock-boundary hook. |

## Findings

Severity is about **what happens if we do nothing**, not about how ugly the code looks.

### F-01 · 99 endpoints block the event loop on every query — *severity: medium-high*

**What:** the database session is synchronous (`create_engine` + `sessionmaker`, `def get_db`),
but 109 endpoints are declared `async def` and issue DB calls directly. FastAPI runs a plain
`def` endpoint in a threadpool; an `async def` one runs *on the event loop*, so every query
those endpoints make stalls **all** concurrent requests served by that worker. Production runs
4 uvicorn workers, so the stall is per-worker.

Of the 109: **99 contain no `await` at all** — they are `async` for no reason and converting
them to `def` is mechanical and behaviour-preserving. The other **10** mix a real `await`
(`await file.read()`, `await _validate_image(file)`) with synchronous `db.commit()`, so they
need the DB work moved off the loop instead (`run_in_threadpool`), one by one.

**Evidence:** `auth.py` (9 endpoints), `author.py` (10), `keys.py`, `health.py`, `dsl.py`,
`llm.py:528/1267/1375`, `projects.py:716`, `media.py:78/132`, `profiles/*`.
Only 2 uses of `run_in_threadpool`/`to_thread` exist in the entire backend.

**This is not about solving.** ADR-007 already removed every in-request solve: the work runs
in Celery and the API only waits. But two `async def` endpoints in `solve.py` do query the DB
on the loop, and one of them matters more than its size suggests:

- **`get_async_solve_status` (`solve.py:1257`)** — the **polling** endpoint. The studio calls
  it repeatedly for the entire duration of every solve, so it is one of the most frequently
  executed handlers in the system, and each call blocks the loop for its query. This is the
  single highest-traffic item inside F-01 and should lead the batch.
- **`cancel_async_task` (`solve.py:1362`)** — same shape, far lower traffic.

Both are in the mechanical group (no `await` in the body), so both are a keyword change.

**Why it is not worse:** most of these queries are single-row and fast, and the solve itself
never runs here. This is a ceiling on concurrency, not a present outage.

**Fix:** mechanical for 99; case-by-case for 10. See **ADR-009**.

### F-02 · The public health endpoint blocks the loop for 100 ms per call — *severity: medium*

**What:** `GET /api/v2/health` is public, `async def`, and calls
`psutil.cpu_percent(interval=0.1)` — a **blocking 100 ms sleep** executed on the event loop.
Docker's own health check hits it on a schedule, and that traffic is classified as trusted
internal, so it is **exempt from the 60/min public rate limit**.

**Evidence:** `app/api/v2/health.py:103`; the rate-limit exemption is in
`auth_middleware.py` (`is_trusted_internal_request`).

**Fix:** `interval=None` (non-blocking, reads the delta since the previous call) and/or make
the endpoint `def`. Roughly a two-line change; listed separately from F-01 because it is the
single most-called endpoint in the system.

### F-03 · CI has no security gate at all — *severity: medium*

**What:** no `bandit`, no `pip-audit`, no `safety`, no `npm audit`, no image scan — not in
`.github/workflows/`, not in `.pre-commit-config.yaml`. The frontend `npm audit` gate is
known to have disappeared (recorded 2026-07-25); this audit confirms the backend never had an
equivalent. Nothing in the pipeline would notice a dependency advisory.

**Root cause (found while fixing it):** the gates were not deleted — they lived in
`.woodpecker/woodpecker.yml` and did not survive the migration to GitHub Actions. `app/CLAUDE.md`
kept stating that CI ran `bandit` and `pip-audit`, so their absence was invisible.

**✅ FIXED (D-11, 2026-07-26).** Three gates added to `.github/workflows/ci.yml`:

- `pip-audit -r requirements.txt` — **strict**. Declared production dependencies (and their
  transitives) are clean today, so any new advisory fails the build.
- `bandit -r app/ -lll` — **HIGH only**, and clean today. Bandit reports 5 medium / 31 low,
  mostly f-string SQL over hardcoded table names in migration backfills; gating at medium
  would have failed on day one and taught everyone to ignore the pipeline.
- `npm audit --audit-level=critical` — blocking, plus a non-blocking `high` step so the known
  advisories stay visible in the log.

**Why the frontend gate is `critical` and not `high`:** the 5 high advisories are all
transitive — `postcss` and `sharp` through Next, plus `js-yaml`/`brace-expansion` — and npm's
only offered fix is a downgrade to `next@9.3.3`. Worth recording: running plain
`npm audit fix` (the non-breaking one, which the report advertises for three of them) took the
count from **5 high to 14** by reshuffling the tree, so it was reverted. Re-check when Next
ships a release that bumps postcss/sharp.

### F-04 · The domain layer imports upward — *severity: medium (architectural)*

**What:** ADR-001 makes `app/domains/` the extracted, self-contained layer, yet:

| Direction | Count | Example |
|---|---|---|
| `domains → services` | 10 | `domains/solver/time_limits.py:54` |
| `domains → api` | 7 | `domains/solver/routes/file_export.py:18` |
| `shared → services` | 9 | `shared/core/auth_middleware.py:18` |

The `domains → api` edges come from the solver's own `routes/` package, so some are
legitimately "a domain owning its HTTP surface" — but they still reach into `app.api` for
shared dependencies, which is what makes the domain non-extractable today.

`shared → services` is the one that is simply a **gap in the contract**: `import-linter`
forbids `shared → domains` but says nothing about `shared → services`, so the base layer
depends on the layer above it and nothing complains.

**Fix:** add the missing contract(s), then unpick the edges they reveal. The `shared` one is
worth doing first because it is the cheapest and closes a hole in an existing guarantee.

### F-05 · No layer contract on the api → services → domains direction — *severity: medium (architectural)*

**What:** the 6 existing contracts protect sideways boundaries (domain vs domain, shared vs
domains, purity of the compiler). **None** protects the vertical direction, which is why F-04
could happen silently. Every violation above was found by this audit, not by the gate that
exists precisely to find them.

**Fix:** one `layers` contract in `pyproject.toml` expressing
`api > tasks > services > domains > models/schemas > shared`, added with the current
violations listed as explicit exemptions so it goes green on day one and ratchets from there.

### F-06 · 55 endpoints return `dict[str, Any]` — *severity: medium (contract)*

**What:** 55 route handlers declare `-> dict[str, Any]` with no `response_model`, so the
generated OpenAPI describes them as free-form objects. The frontend then cannot use its
generated types for those endpoints and falls back to hand-written ones — which is exactly
how a contract drifts without CI noticing (`solvers.py` is the known case; the frontend
consumes hand-written `SolverInfo`/`SolverCapabilities` for it).

**Fix:** incremental — each endpoint typed with a Pydantic response model is one less place
the contract can drift. Regenerating `frontend/src/lib/generated/api.ts` after each batch is
already a CI-gated step (`contract-types`).

### F-07 · 113 `Depends(get_db)` instead of the project's own aliases — *severity: low (consistency)*

**What:** `app/api/deps.py` defines `DBSession`, `CurrentUser`, `CurrentOrg`, `AdminUser`,
and the project rule says to use them. 113 call sites still write `Depends(get_db)` directly
(`execution.py` 10, `author.py` 10, `auth.py` 10, `solve.py` 6, …). Both work; having both is
the problem, because "which one is right" has to be re-decided on every new endpoint.

**Fix:** mechanical, and best done in the same pass as F-01 (both edit the same signatures).

### F-08 · 23 foreign keys have no index — *severity: low-medium (scales badly)*

**What:** PostgreSQL does not index foreign keys automatically. 23 FK columns have no index
starting with that column, so joins on them scan, and any `DELETE`/`UPDATE` of the parent row
scans the child table to enforce the constraint.

The ones on hot, multi-tenant paths: `users.organization_id`, `api_keys.user_id`,
`refresh_tokens.user_id`, `model_executions.executed_by_user_id`, `model_projects.created_by`,
`model_projects.workspace_id`, `llm_conversations.organization_model_id`.

**Why it has not hurt:** current table sizes are small enough that a sequential scan is fast.
It gets worse strictly monotonically with adoption.

**Fix:** additive-only migration adding the indexes (`CREATE INDEX CONCURRENTLY` where the
table is non-trivial). No schema risk, no rollback risk.

### F-09 · Data access lives in the route layer — *severity: low-medium (architectural)*

**What:** 187 direct `db.query(...)` / `select(...)` statements sit in `app/api/`, i.e. the
routes are also the data layer. Concentrated in `routes/admin/organizations.py` (19),
`routes/profiles/reviews.py` (13), `routes/models/execution.py` (13), `auth.py` (12).

This is why `app/api` is 14,653 lines, and why `execution.py` keeps growing (839 lines today,
~740 when it was first flagged). It also means a multi-tenancy filter is re-typed by hand at
every call site — it happens to be right everywhere today (see "healthy"), but the safety
depends on vigilance rather than on structure.

**Fix:** not a big-bang. The credible version is: when a route file is touched for another
reason, lift its queries into the owning service. `execution.py` is the natural first case,
since it is already flagged for extraction.

### F-10 · `app/services/` holds six bounded contexts — *severity: low (known, planned)*

**What:** `app/services/` (16,186 lines) contains BC2 Marketplace, BC4 Identity, BC5 AI
Assistant, BC6 Automation, BC7 Observability and BC8 Platform Admin side by side. This is
**already documented** in `docs/BOUNDED_CONTEXTS.md` with an extraction order, so it is a
planned state rather than a discovery — recorded here for completeness, and because the
extraction order is the thing v4.0 will want settled.

Largest files, as a proxy for where the seams are: `dsl/compiler.py` 2,312 · `llm.py` 1,533 ·
`solve.py` 1,412 · `settings_registry.py` 1,283 · `mdpdp.py` 1,240 · `projects.py` 1,148.
(`compiler.py` being the biggest is fine — it is a compiler, and it is a *pure* one, enforced
by its own contract.)

### F-12 · The API container is sized for solves that no longer happen there — *severity: low (stale rationale)*

**What:** `deploy/docker-compose.prod.yml:199-201` justifies the API container's 5 GB / 6 CPU
limits with *"4 uvicorn workers + SCIP sync solves on large models — sync solves of large
models (tens of thousands of vars) are memory- and CPU-hungry"*.

Since **ADR-007** (accepted 2026-07-04) no solve executes in the API process: every solve is
enqueued to Celery, and the API only waits for the result. The stated reason for those limits
no longer exists.

**Why it is harmless today:** the comment itself notes the cap is "a ceiling, not a reserve",
so nothing is being wasted — the container simply may claim less than it is allowed.

**Why it still matters:** it is the kind of stale rationale that misleads the next capacity
decision (someone sizing the box, or wondering why the API needs 6 CPUs). Worth a comment fix
and, if anyone re-tunes the VM, a genuine measurement of what the API process needs now that
it only orchestrates.

### F-11 · Inherited debt from §5, still open — *severity: low, but blocks a tool*

Legacy `DROP`s (`model_catalog`, `organization_models`, and the dead FK columns), the
`/api/v2/seller/*` → `/author/*` wire rename (9 references), and the 11 SQLAlchemy-1.x
`Column()` declarations in `app/models/favorite.py`. Until the dead tables and columns go,
`alembic --autogenerate` cannot be trusted, which taxes every future migration.

**Constraint (as of 2026-07-26; the additive-only rule was dropped 2026-08-02):** the `DROP`s could only ship in a release
that can no longer roll back to code reading those columns. That makes this a **release-shaped**
task, not a refactor — it needs its own window.

## Explicitly NOT proposed

- **Microservices** — discarded by the owner (2026-07-25). Not studied, not measured, not
  revisited. The modular monolith stands.
- **Making `auto_router` read capabilities dynamically** — already decided against with a
  written rationale: its reason slugs carry solver names and are public API contract, so a
  dynamic tree would either lie in the slug or grow dead branches. Each branch's assumptions
  are pinned by tests instead. *(Still true of the tree. Since 2026-08-18 the router does
  consult capabilities on one path only — substituting when the solver a branch names is not
  installed on this server — and that path carries its own slug, which names no solver
  precisely so it cannot lie. The branches themselves are unchanged.)*
- **Async SQLAlchemy migration.** F-01 does *not* call for it. Converting endpoints to `def`
  gets the same concurrency benefit for a fraction of the cost and risk; rewriting every query
  to `async` sessions would touch the whole backend to reach the same place.
